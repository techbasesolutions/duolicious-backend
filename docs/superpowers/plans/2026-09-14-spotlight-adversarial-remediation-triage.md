## Remediation scope, Wave 1 (consent and lifecycle invariants), proposed

All in `ahavah-api` unless stated; each item lands with tests that encode the desired behaviour (the probes' assertions inverted).

1. **Content revisions and revision-bound consent (F01, F11).** New table `spotlight_revision` (queue request, revision number, rendered asset hash, image key, photo uuid, caption, fields shown, layout version, channels, participant set as jsonb, created_at). `publishing_queue` rows reference `current_revision_id`. Member approval writes `spotlight_revision_consent(revision_id, person_id, approved_at, token_nonce)`; admin approval is also per revision. Any material edit (caption, photo, participants) creates a new revision and clears both approvals; in-flight (`scheduled`, `processing`) revisions are immutable (409). Roundups require consent from every pictured member for that roundup revision, or fall back to the count-only variant. Confirm and card tokens carry a stored single-use nonce and a consent epoch on `person` (`spotlight_consent_epoch` incremented on opt-out); replay after withdrawal is rejected. Preview before approval: E4 links to a page that shows the rendered revision, which means rendering must happen before E4, not after (see decision 2).
2. **Fail-closed final check (F02).** `GET /queue/<id>/eligible` validates: lease held and current, revision consent present for every pictured person, each pictured person activated and not deleted, the exact approved photo uuid still present and approved, queue status still `processing`; a subject-bearing row with a null subject is not ok; roundup rows validate every tile.
3. **One withdrawal operation (F03).** `withdraw_member(tx, person_id, reason)` called from opt-out, `DELETE /account`, admin delete or ban, the pending-deletion cron, and moderation actions: cancels future rows, invalidates roundup participation (new revision without the member or count-only), files removal work for published rows before the person row can be erased (removal task rows carry a copied external id and platform so they survive `ON DELETE SET NULL`), and excludes the member from every email selection (`_Q_SPOTLIGHT` also filters `activated AND deletion_requested_at IS NULL`).
4. **Delivery state separate from withdrawal (F04).** `publishing_queue` gains `cancellation_requested_at`, `lease_token`, `delivery_state` (`none`, `attempting`, `published`, `delivery_unknown`, `failed`). `cancel_for_member` sets `cancellation_requested_at` and cancels only rows not `attempting`; `complete(published)` with a matching lease token is accepted even after cancellation, stores the external id, and files a removal task immediately. Timeouts after a sent publish call become `delivery_unknown` and require reconciliation or an explicit operator decision before any retry. The worker reports receipt-persistence failures as their own count and never counts an unacknowledged publish as success.
5. **Feature occurrence (F05).** `spotlight_occurrence(id, kind, person_id, request_key, created_at)`; cooldown checks the occurrence, not the row; sibling channel rows of one occurrence pass; roundup pictured members get occurrences too. E5 is sent once per occurrence when the first channel confirms, with the real post URL (Facebook now; Instagram once the permalink is fetched via the media id at completion).

## Remediation scope, Wave 2 (recoverable external effects), proposed

6. **Immutable storage (F06).** Object keys include the revision id and asset hash; decode the PNG (Pillow) and check dimensions and size before upload; attach a revision only if the expected state still matches (compare-and-set on `current_revision_id` and status); rejected uploads enqueue a deletion job; pending-approval assets are served through short-lived signed URLs, never public until approved.
7. **Durable mail outbox (F07, F08).** `email_outbox(id, campaign, campaign_id, person_id, payload, state, attempts, provider_message_id, reserved_at, sent_at)`; reservation is the idempotency point (unique on campaign, campaign_id, person); the runner reserves, sends, then marks `accepted` or `acceptance_unknown`; suppression re-checked at send; broadcasts become resumable jobs (the admin endpoint enqueues and returns a job id; a worker loop drains). E4 and E5 are enqueued in the same transaction as the candidate or the receipt; the Growth tab shows invitation state and can resend the same request.
8. **Cleanup jobs (F09).** `cleanup_job(kind: platform_removal | asset_delete, target, state, attempts, evidence)`; `delete_images` reports confirmed deletions per key and keeps keys until confirmed; retention and removal done clear references only after confirmed deletion; external deletion runs outside the transaction; cleanup runs regardless of the publication pause; a separately named emergency stop (`external_access_enabled`) halts every external call and alerts on outstanding work; Graph "does not exist" is treated as absent only for the exact error code Meta documents, permission errors go to investigation.

## Wave 3 and 4

As the review sequences them: renderer, exact-card approval page with preview, privacy switch, confirmation page, Growth panels (all still design-gated); attribution rebuilt on visitor-bound click receipts (F10); controls made honest (F12: invite pause, publication pause, emergency stop; auto flags implemented with revision-bound consent or removed; welcome cohort by sign-up time; weekly business key for roundups; idempotent ticks); then the release acceptance matrix in staging before any live post.

## Decisions for the owner before the plan is written

1. **Preview before approval (F01).** Rendering must precede E4, so the renderer (Task 5, design-gated) is on the critical path for consent. Options: (a) block Wave 1 completion on the design handoff; (b) render the preview with a temporary plain layout now and re-render with the designed template as a new revision that requires re-approval; (c) implement revisions now and keep approval disabled until the renderer exists. Recommendation: (c), and treat the handoff as the gate for enabling approvals at all.
2. **Roundup consent.** Require every pictured member's approval of the exact roundup revision (an E4 per member per roundup), or ship count-only roundups until that exists. Recommendation: count-only until the per-member roundup approval flow is built; it removes the largest consent surface at launch.
3. **Mail semantics.** Accept "at-least-once with visible uncertainty" for campaign email (a crash between SMTP acceptance and the log can still produce a duplicate, now surfaced as `acceptance_unknown`) rather than promising exactly-once. Recommendation: accept.
4. **Migration policy for existing rows.** Existing unpublished candidates return to explicit re-approval under revisions; existing receipts and removal work are preserved. Since nothing is deployed, the branches can be reworked before any migration ships; confirm that nothing from these branches has been merged anywhere.
5. **Activation stance.** Adopt the review's release acceptance matrix as the gate for the first live post, run in a staging environment first. The current Phase A and B branches stay unmerged until Wave 1 lands on them.
