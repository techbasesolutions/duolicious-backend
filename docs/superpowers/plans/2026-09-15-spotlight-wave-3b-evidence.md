## What the reviews caught

- **A serialization failure would have failed an entire sign-up, not just its attribution.** Task 3's own first-round comment claimed a lost concurrent claim under `REPEATABLE READ` would "quietly match zero rows," reasoning that held for read-committed but not for this database's actual isolation level. Measured directly with a three-connection probe rather than trusted: the loser genuinely raises `psycopg.errors.SerializationFailure`, and a bare `try`/`except` around it (the reviewer's first-round prescription) still leaves the transaction in `InFailedSqlTransaction`, refusing every later statement, so the whole finish-onboarding request would 500 and the member's graduation would roll back merely because their attribution lost a race. Fixed with a `SAVEPOINT` around the consuming `UPDATE` and `ROLLBACK TO SAVEPOINT` on a lost race, proven correct by mutation testing both the naive fix (still red) and no fix (still red) against a real two-connection race, with the fix itself green.
- **The dropped User-Agent would have made bot filtering useless.** Once `ahavah-web`'s `/s/[key]` route started calling the Flask API itself with a server-side `fetch()` instead of letting the browser redirect straight through, that outbound request carried Node's own default headers, not the visitor's. `_ua_class`, the function that decides whether a click is a bot, reads nothing but the `User-Agent` header, so every click, crawler included, would have classified as human, always minting a receipt and defeating the fraud protection the receipt exists for, while also silently regressing the pre-existing `ua_class` analytics column for every `/s/<key>` click, Spotlight or not. Caught in Task 5's review as a CRITICAL finding, fixed by forwarding the incoming request's `User-Agent` verbatim, and proven by a test that stubs `fetch` to capture the header it was called with and a Facebook-crawler string reaches it intact.
- **The `ua_class <> 'bot'` clause in the consuming `UPDATE` had no test and would have survived deletion.** Because `record_click` never mints a receipt for a bot, no receipt could ever match that clause through normal use, so the belt-and-braces predicate was dead code from the test suite's point of view even though it was live in the source. Caught in Task 3's review, closed by forcing a receipt directly onto a bot row with a raw `UPDATE` and asserting redemption still fails, then proving the clause load-bearing by deleting it and watching the new test go red.
